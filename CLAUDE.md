## Architecture

Data pipeline: `cli.ts` -> `export.ts` -> {`granola.ts`, `extractor.ts`} -> `converter.ts` -> `writer.ts`

Three data sources per meeting:

1. **`granola meeting list -o json`** -- metadata: title, date, people, calendar event, notes (ProseMirror)
2. **`granola meeting transcript <id> -o json`** -- utterances with speaker source and timestamps
3. **`granola meeting enhanced <id> -o json`** -- AI summary as ProseMirror JSON

## Key Files

- `src/cli.ts` -- CLI entry point (Commander, dynamic version, signal handlers, `--json` flag, rich help text)
- `src/export.ts` -- orchestration: `runExport(options)` function
- `src/config.ts` -- business rules and defaults (timezone, speaker map, LLM schema, slug constraints)
- `src/granola.ts` -- shells out to granola-cli, parses JSON, auth retry
- `src/converter.ts` -- core transformation: GranolaMeeting + transcript + enhanced -> Minutes markdown
- `src/prosemirror.ts` -- ProseMirror JSON -> Markdown converter (recursive, not a library)
- `src/extractor.ts` -- LLM extraction via `claude -p --json-schema`
- `src/writer.ts` -- atomic file writes with gray-matter
- `src/utils.ts` -- shared utilities (error handling, typed error classes)
- `src/types.ts` -- all TypeScript interfaces

## Implementation Patterns

These are non-obvious decisions and gotchas not discoverable by reading the code alone:

- **Timezone is hardcoded to Singapore UTC+8.** `config.ts` defines `TIMEZONE.offsetMinutes = 480`. All date conversions in `converter.ts` use `toLocalDate()` which applies this offset manually. There is no locale detection.
- **Speaker attribution is binary.** Granola only provides `microphone` vs `system` audio source, not individual speaker IDs. SPEAKER_0 = meeting creator (from `people.creator`), SPEAKER_1 = "Remote participants" (everyone else). This is a Granola limitation, not a design choice.
- **Auth tokens expire during long runs.** `granola.ts` catches 401 errors and re-runs `granola auth login` before retrying. Credentials refresh every 10 minutes (`AUTH_REFRESH_INTERVAL_MS`). This was added after tokens expired during 25+ minute export runs.
- **500ms rate limiting between API calls.** `granola.ts` adds a `DELAY_MS` pause before each transcript/enhanced API call to avoid overwhelming granola-cli.
- **Atomic writes via tmp+rename.** `writer.ts` writes to a `.tmp` file then renames, ensuring no partial files on disk. Collision handling appends `-2`, `-3`, etc. up to 99 attempts, then **throws** — it used to fall through to the un-suffixed slug and overwrite the meeting already exported under that name. The tmp filename carries a random suffix and is created with `flag: "wx"`, so a symlink pre-planted at a predictable `<slug>.md.tmp` is neither guessable nor followed.
- **`matter.stringify` must keep its options argument, and `lineWidth: -1` is a security control.** js-yaml folds any frontmatter scalar over 78 characters into a `>-` block whose continuation lines sit at column 2 — and Minutes' `extract_field` is a *line scanner*, not a YAML parser, returning the first `line.trim()` that starts with the key. A crafted long title therefore puts `date: 2099-...` on a fold line and forges the field for the FTS date column, the dashboard, and the text-import walk, while `serde_yaml` still reads the real one. The `as unknown as Parameters<typeof matter.stringify>[2]` cast is required or `pnpm build` fails with TS2353: gray-matter forwards the options to `safeDump` at runtime but does not declare them in `GrayMatterOption`. Passing a truthy options object also disables gray-matter's unbounded module-level cache. Guarded by a contract test that drives the real `convertMeeting` + `writeMinutesFile` and a port of `extract_field` — a standalone `matter.stringify` assertion cannot regress-guard the sink.
- **Two independent guards keep output inside `--output-dir`.** `toLocalDate` returns a `1970-01-01` sentinel rather than its raw input, because `buildSlug` splices `date.slice(0, 10)` into the filename unsanitized; and `writeMinutesFile` asserts `dirname(resolve(filePath)) === resolve(outputDir)` before writing. Neither is reachable today (`created_at` is Granola's server-side timestamp, and the title half of the slug survived an exhaustive fuzz of all 1,114,112 code points) — they exist so a future slug change cannot quietly become a traversal.
- **`prosemirror.ts` clamps what it reads from `attrs`.** `node.attrs.level` is untyped third-party JSON: unclamped, `"#".repeat(level)` turns a ~90-byte node into a multi-hundred-megabyte string. Levels clamp to 1-6 and the recursive walk stops at depth 100.
- **Untrusted strings are laundered through `stripControlChars` on BOTH the terminal path and the frontmatter path, and the second one is a security control.** Meeting titles come from calendar invites. On stderr, raw escapes repaint the operator's screen or (via OSC 52) reach the clipboard — display integrity. In frontmatter, a bare newline is the *other half* of L-1: `lineWidth: -1` stops js-yaml folding a long scalar, but a value that already contains a newline is still emitted as a `|-` block with column-2 continuation lines, which `extract_field` reads as top-level keys exactly as it read the fold lines. Do not "simplify" `cleanFrontmatter` in `writer.ts` back to a plain `stripEmpty` — the contract suite has a newline case that will catch you, and it exists because this was missed the first time.
- **LLM extraction is optional.** `extractor.ts` checks for `claude` CLI availability once (cached at module level in `claudeAvailable`). Returns null on any failure, never blocks the export pipeline.
- **The `claude` subprocess is deliberately tool-less, and `--tools ""` is the whole control.** Meeting titles come from calendar-invite summaries, so anyone who can send an invite writes text that lands in the extractor's prompt. Structured output does *not* disable tools, and print mode still runs the built-in read-only Bash set (`head`, `grep`, `find`, `strings`, ...) with no prompt — so without `--tools ""` that text drives an agent holding the user's credentials. `""` is the CLI's own documented value for "no tools" (`claude --help`: *'Use "" to disable all tools'*). The cwd pin and `--system-prompt` (replaces the base prompt; `--append-system-prompt` extends it) are the second and third layers. That pin must point at a **`mkdtempSync` directory, never at `tmpdir()` itself** — `/tmp` is mode 1777 on Linux and whenever `TMPDIR` is unset, so pinning there would let any local user plant `/tmp/.claude/settings.json` hooks and hand the subprocess exactly the config the pin exists to avoid. Do not add `--strict-mcp-config` — it errors out on enterprise-managed machines.
- **The model's JSON is rebuilt, not trusted.** `parseInsights` reconstructs `structured_output` from a fixed key whitelist, so no string the model emits is ever used *as* an object key and `__proto__` cannot ride into frontmatter. `INSIGHTS_SCHEMA` is a *request* to the model; this function is the enforcement. Widening the frontmatter means editing both.
- **`spawn`'s `timeout` does not bound the promise.** It only raises SIGTERM, and `close` does not fire while any descendant still holds the stdout pipe — a grandchild keeps the promise pending forever. `spawnClaude` therefore runs its own `setTimeout` -> SIGKILL at `LLM.timeout + LLM.killGraceMs`.
- **The extractor's stdin mock must be a real EventEmitter.** `spawnClaude` attaches an `error` listener to `proc.stdin` (an undrained pipe on a >64 KiB write raises EPIPE, which otherwise escapes both try/catch layers and kills the entire export run). A `{ write, end }` stub makes that line throw at runtime while every other assertion still passes, so `tests/integration/extractor.test.ts` builds stdin from `EventEmitter`.
- **Module-level state.** `extractor.ts` caches `claudeAvailable` and `granola.ts` caches `lastAuthRefresh` at module scope. Tests that exercise these need `vi.resetModules()` between test cases.
- **Minutes consumer contract is enforced by `tests/contract/`, not by hand.** Required frontmatter is `title`, `type`, `date`, `duration`; `action_items` status must be `"open"` or `"done"` — but note **ajv cannot check that last one**: in the published schema `ActionItem.status` and `Intent.status` are a bare `{"type": "string"}` and only `OutputStatus` carries an enum. A dedicated contract test covers it instead, because upstream *silently ignores* a status outside the pair, so a bad value vanishes from `minutes find-open-actions` with no error at either end. Upstream `OutputStatus` now has **four** values — `complete`, `no-speech`, `transcript-only`, `degraded` — but this tool emits only the first three (`degraded` means a post-transcript pipeline step failed; we have no such step, so it stays out of `MinutesFrontmatter["status"]`). Do not hand-verify any of this: change frontmatter and run `pnpm test`.
- **Upstream has two `Frontmatter` structs and the published schema tracks neither perfectly.** `schema/meeting.schema.json` is hand-maintained (18 properties, `required` includes `duration`); the insta snapshot generated by `minutes schema` from `minutes_core::markdown::Frontmatter` has 32 and drops `duration` from `required`; `crates/reader/src/types.rs` is the struct that actually parses our files. We validate against the published schema and watch all three for drift. Full reasoning in `tests/contract/PROVENANCE.md` — read it before touching the vendored schema.
- **ajv needs two non-obvious things to compile that schema.** Its default export is the Draft-07 class and throws on `$schema` 2020-12 — use `Ajv2020` from `ajv/dist/2020.js`. And the schema carries `format: "uint64"`, which `ajv-formats` does not define while strict mode throws on unknown formats — register it by hand. Both failures happen at `compile()` and look like "the vendored schema is broken".
- **Every `uses:` is pinned to a 40-character commit SHA, and the repo enforces it.** `sha_pinning_required: true` on `repos/.../actions/permissions` rejects an unpinned reference outright, so a mutable-major-tag `uses:` will not merge. This is the tj-actions/changed-files class (CVE-2025-30066, ~23,000 repos): a moved upstream tag runs attacker code inside a job that holds `id-token: write` for npm and, in the other job, the release-please App private key. **Provenance is not a mitigation** — SLSA attests *where* a build ran, never *what* it produced, so a poisoned workspace ships attacker bytes under a signature that passes `npm audit signatures`. When resolving a new pin, use `gh api repos/OWNER/REPO/commits/vN --jq .sha` — reading `refs/tags/vN` gives the *annotated tag object* SHA (e.g. `f520ece…` for `pnpm/action-setup@v6`), which Actions will not accept. `.github/dependabot.yml` bumps the pins on a reviewed PR; without it, pinning just trades a supply-chain risk for an unpatched-dependency one.
- **`v*` tags are protected by ruleset `release-tag-protection` (id 21071296), and only the release-please App can write them.** `bypass_actors` is the App (id 3269344) alone — deliberately *not* repository admins. GitHub loads a workflow file from the **release tag's own tree**, and npm's trusted-publisher config pins owner + repo + workflow *filename*, not the ref or the file contents (proven empirically: 0.4.2/0.4.3 published from `refs/heads/main`, 0.5.0 from `refs/tags/v0.5.0`, under one config). So an arbitrary `v*` tag was a path to the registry that never transited branch protection. If you ever need to retag by hand (see the release-event/tag-ref note below), drop or edit the ruleset first: `gh api -X DELETE repos/calvindotsg/granola-to-minutes/rulesets/21071296`.
- **`npm-publish` is a GitHub Environment with a required reviewer, so a release waits for a human.** The job cannot mint its OIDC token until the deployment is approved. **The other half of this control lives at npm**: add the environment name to the trusted-publisher config there, because that is the only check enforced *outside* this repository — it still holds if the repo itself is compromised. Until that is done the environment is a repo-side speed bump, not a boundary.
- **The contract-drift issue is matched by label, never by title.** A title is not a namespace: any GitHub user could pre-create "Minutes frontmatter contract has drifted upstream" and capture every future drift report into a thread they control. The label is the whole control — applying one needs **triage permission**, so an outsider cannot attach `contract-drift` to an issue they open. Do **not** add `--author app/github-actions` alongside it: that is GitHub *search* syntax, `gh issue list --author` returns nothing for it, and the dedup then silently fails open and files a fresh issue on every drift run. **The `contract-drift` label must exist** — `gh issue create --label` errors on a missing label.
- **The `audit` job reports and never gates.** `pnpm audit` is red today and will stay red: 3 of the advisories are gray-matter's pinned js-yaml 3.x (the parser CVEs — unreachable, because the only `load` path this tool can reach is gray-matter parsing its own body argument, which `writeMinutesFile` guards) and the rest are dev-only. A gate would be permanently red and train everyone to ignore it, so the job writes the counts to the step summary and exits 0. Dependabot security alerts do the actual alerting.
- **Branch protection via ruleset, and the required check is named exactly `test`.** `main` is protected by ruleset `main-protection` (id 14668976): PRs required, `bypass_actors: []`, `current_user_can_bypass: never`. Managed via `gh api repos/calvindotsg/granola-to-minutes/rulesets` — never legacy branch protection.
- **Never put a `strategy.matrix` on the job whose id is `test`.** A matrix renames the published check runs to `test (22)`, `test (24)`, … so nothing reports the bare `test` context and **every PR hangs forever** at "Expected — waiting for status", with no bypass available. `test.yml` therefore runs the matrix as `test-matrix` and fans in to a job whose id is exactly `test`. A static `name: test` on the matrix job is not a substitute: duplicate contexts resolve to the most recent report, so a failing leg can be masked by a later-finishing passing one. The check-run status can also lag the job by minutes — all steps ✓ while `gh pr checks` says pending is propagation lag; `gh run rerun --job <id>` clears it.
- **Contract drift is watched on `push` as well as `schedule`.** GitHub disables scheduled workflows on public repos after 60 days of inactivity, and this repo has gone quiet that long before — a cron-only monitor would die exactly when needed. `scripts/check-contract-drift.mjs` runs locally too: exit 0 in sync, 1 drift, 2 upstream unreachable (unreachable is deliberately not drift and opens no issue).
- **Binaries are resolved in-process, not with `which`.** `src/which.ts` walks `PATH` the way `execvp` does. Shelling out to `which` only moved the problem — `which` is itself a bare name resolved at spawn, is absent from minimal container images, and lives outside `/usr/bin` on NixOS. `granola.ts` resolves once and reuses the result across all 200+ calls of an export, so the binary answering call 200 is provably the one `ensureAuth` checked. Two deliberate deviations from `execvp`: empty and *relative* `PATH` entries are skipped (the cwd is not a place to accept a binary from), and the result is **not** `realpath`'d, because package managers install CLIs as symlinks and a pinned inode would break on upgrade mid-run. It lives in its own module rather than `utils.ts` on purpose: `utils.ts` is imported by `converter.ts` and `writer.ts`, whose tests mock `node:fs` with partial factories.
- **Exit codes are a machine contract, so usage errors get their own.** `InvalidOptionError` -> 3, mapped in `cli.ts`. Before it existed, a bad `--note-id` or `--since` fell through to the `unhandledRejection` handler and exited 1 — the code the help text documents as "granola-cli not installed", which is unreadable to anything parsing `--json`. Option validation also runs *before* the prerequisite check, auth, and `listMeetings()`: a mistyped flag should not cost an auth round-trip and a full account listing first. Commander's own usage errors (unknown option) still exit 1; that is accepted rather than fought with `exitOverride`.
- **Dynamic CLI version via `createRequire`.** `cli.ts` reads version from `../package.json` at runtime using `createRequire(import.meta.url)`. Cannot use `import pkg from '../package.json'` because ESM (`type: "module"`) requires `resolveJsonModule` in tsconfig which isn't enabled. Path `../package.json` resolves from `dist/cli.js` at runtime. Never hardcode the version string.
- **`--json` mode suppresses progress, not errors.** The `log()` helper in `export.ts` gates progress/info messages behind `!json`. Error messages (line 140) always go to `console.error` regardless of mode — matching `gh`/`kubectl` convention. Agents parsing stdout JSON won't see interference from errors on stderr.
- **npm publish uses OIDC trusted publishing.** No `NPM_TOKEN` secret exists. The `npm-publish` CI job authenticates via GitHub Actions OIDC (`id-token: write` permission). If publishing fails with auth errors, check `npm trust list granola-to-minutes` — do not create a new npm token as a first response.
- **Never run `npm login` locally for this package.** It writes a plaintext `_authToken` into `~/.npmrc` that no workflow needs: the package is public (reads are unauthenticated), publishing is OIDC-only, and from Aug 2026 npm requires an interactive 2FA session for account/package changes — so a stored token cannot perform them anyway. Do authenticated one-offs (`npm access`, staged-publish approval) with a just-in-time env var and no file: `env "npm_config_//registry.npmjs.org/:_authToken=$(op read 'op://Personal/granola-to-minutes-npm/credential')" npm <cmd>`. That 1Password item currently holds a **revoked** value (notes: "REVOKED 2026-04-05"), so the recipe only works once a live token is stored there — which, per the bullet above, should be rare to never. Do **not** park `_authToken=${NPM_TOKEN}` in `~/.npmrc` as a substitute — when the variable is unset npm sends the literal string `Bearer ${NPM_TOKEN}` rather than omitting the header, producing confusing 401s.
- **Release workflow has two jobs with different auth.** `release-please` uses a GitHub App token (to trigger CI on its PRs). `npm-publish` uses OIDC (no npm token). They cannot share credentials — keep them as separate jobs.
- **`package-name: ""` is what empties the release-please component. `component: ""` does nothing.** If a release PR merges and no tag ever appears, this is the cause — not permissions, and not the tag ruleset. `BaseStrategy` does `this.component = options.component || normalizeComponent(this.packageName)`, so an empty-string `component` is **falsy and silently discarded**, falling back to package.json's name. Meanwhile `separate-pull-requests: false` runs the Merge plugin, which rebuilds the grouped PR on branch `release-please--branches--main` with **no** component. The release phase then compares the branch's component (undefined) with `getBranchComponent()` (`granola-to-minutes`), logs `⚠ PR component: undefined does not match configured component: granola-to-minutes`, skips the release, and aborts with `⚠ There are untagged, merged release PRs outstanding`. Note `getBranchComponent()` does **not** honour `include-component-in-tag: false`, though `getComponent()` does — that asymmetry is the whole bug. Setting `package-name: ""` makes both sides `""` and they match. v0.5.0 was tagged **by hand** because of this; `#35` claimed to fix it with `component: ""` and did not. Reproduce locally without pushing anything: `npx release-please@17 github-release --repo-url=calvindotsg/granola-to-minutes --token=$(gh auth token) --dry-run --debug` — a healthy run ends `Would tag 1 releases`, a broken one `Would tag 0 releases`.
- **`bump-minor-pre-major` keeps breaking changes on 0.x.** Without it, a single `BREAKING CHANGE:` footer makes release-please jump 0.4.3 straight to 1.0.0. The flag is set in `release-please-config.json`. Leave it: this tool reads Granola's *internal* API, which upstream documents as liable to change without notice — that is not a 1.0 stability promise. Check the version in the release PR's title before merging it.
- **`actions/create-github-app-token` and `release-please-action` are pinned behind latest on purpose.** They sit in `release.yml`'s auth path, which only runs on `main` after a merge, so no PR can verify a bump. Upgrade them deliberately and watch the next release, not as part of a batch.
